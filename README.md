# きゅうくらりんリズムゲーム

[きゅうくらりん](https://www.nicovideo.jp/watch/sm39257413)のMVを模したリズムゲームである。
課題曲(音声ファイル)をアップロードすると、リズムの解析が行われる。
再生ボタンを押すと課題曲の再生が始まる。同時にマイクによる入力を受け付ける。
ユーザは再生中、手拍子や足踏みなどによってリズムを取ることができる。
そのリズムが、曲のリズムと一致するとMVが正常に作動する仕組み。

判定はリズム1回ごとに行う(=閾値以上の音圧が瞬間的に入力されるとトリガー)。これが曲の盛り上がりポイント・リズムに一致すればOK。一定のOK範囲外ならNG。
OKであればきゅうくらりんのように画面上から画像が一枚降ってくる。
NGであれば画像は降ってこない。

画像の集団は時間経過(数秒に1度)一定距離左に移動していく。
移動はNGで画像が表示されなかった場合でも同様に左に移動する。

例えば、OK→NG→OKなら、NGの箇所だけ歯抜けになった状態で画像の集団が移動していく。
画面内に画像がなくなったらゲームオーバーである。

画像内に1枚以上画像が残っている状態で曲の再生を終えればクリアである。

画像は`./public`内の数字付き画像を用いる。1.pngから順番に登場させ、次の画像がなくなれば1に戻る。
アニメーションは`./Composition.json`を参照すること。(降ってくる→左に動く のセット。)3回OKが続いた場合の映像も`./Composition.mp4`に用意している。

UIは、p5.jsで構築する。ビルドと配信にbunを使用する。その他プログラムはtypescriptで記述する。

## クイックスタート

Bunと、Web Audio APIに対応したモダンブラウザを要する。音声のデコード／再生可否はブラウザが対応する形式に依存する。

```bash
bun install
bun run dev
```

起動後、ターミナルに表示された `localhost` のURLをブラウザで開く。マイク入力にはブラウザの許可に加え、`localhost` またはHTTPSのセキュアな環境が必要。曲の再生音を手拍子として拾いにくくするため、マイク利用時はヘッドホンを推奨。

## 操作方法

| 操作 | 動作 |
| --- | --- |
| `曲を選ぶ` / `O` / `U` | 音声ファイルを選択 |
| `MICを準備` | マイクの許可を求め、入力レベルを調整 |
| マイクの閾値バーをドラッグ | 入力閾値を手動値へ固定（左ほど敏感、右ほど大きな音だけを検出） |
| `AUTO↺` | 手動閾値を解除し、環境音に応じた自動調整へ戻す |
| `NS OFF` / `NS ON` | ブラウザへ要求するノイズ抑制を切り替える |
| `START` / 再生ボタン | ゲーム開始または再開 |
| `Space` | READY画面ではマイクなしで開始、プレイ中は手拍子の代替入力 |
| ステージまたは `TAP` をタップ | プレイ中の手拍子の代替入力 |
| `P` / `Esc` / 再生ボタン | 一時停止・再開 |
| `R` | リザルト画面から同じ曲をリトライ |

マイクの利用が拒否された場合や未対応の場合も、`Space` と画面タップでプレイできる。タブが非表示になるとゲームは自動的に一時停止する。。

## 処理の全体像

```text
音声ファイル
  ├─ analyzeTrack() ── BPM推定 + onset抽出 ── リズムポイント列
  └─ TrackPlayer ──────────────────────────── 曲の再生時刻
                                                     │
マイク ── MicrophoneInput ── 手拍子トリガー ────────┤
Space / タップ ── 手動トリガー ─────────────────────┤
                                                     ▼
                              RhythmGame.registerInput()
                                  │          │
                              タイミング判定  盤面・得点更新
                                  └──────┬───┘
                                         ▼
                                  p5.jsによる描画
```

`index.ts` がファイル選択、解析、再生、入力、ゲーム状態、p5.jsの描画をつなぐ。曲とマイクに関する処理は `src/audio.ts`、UIに依存しない判定と盤面状態は `src/game.ts`  に
分割している。

## エントリポイントから見た処理の流れ

### 1. ページ読み込みと初期化

1. `index.html` がエントリポイントの `index.ts` を読み込みます。`index.ts` は `#app`、非表示の `<audio>`、音声ファイル入力、スクリーンリーダー用通知領域を取得します。要素が欠けていれば `requireElement()` がその場でエラーにし、HTMLとTypeScriptの不整合を見逃さないようにします。
2. `<audio>` を包む `TrackPlayer`、マイクを管理する `MicrophoneInput`、UIに依存しないゲーム状態を持つ `RhythmGame` を1つずつ生成します。この時点のゲームは `idle` で、まだ音声や譜面を持ちません。
3. `new p5(...)` が全画面キャンバスを作り、`public/1.PNG`〜`7.PNG` を並行して読み込みます。画像が読めなかった場合も1×1 pxの代替画像で起動を続け、ゲーム中は番号付きの枠を描きます。
4. 以後、p5.jsの `draw()` が毎フレーム実行されます。ウィンドウ寸法からレイアウトを再計算し、ゲーム更新、ヘッダー、ステージ、フッターの順に描画します。したがってリサイズ時も、ゲームの論理列を変えずに画像の表示位置と画面内判定だけが新しい寸法へ追従します。

### 2. 音声ファイルの読み込み

ファイル入力の `change` イベントから `loadTrack(file)` が始まります。同じ画面で別の曲を選べるため、先に実行中の解析を `AbortController` で中止し、曲とマイクを停止して以前の解析結果を捨てます。

同じ `File` は、ここから目的の違う2経路へ渡されます。

```text
選択された File
  ├─ TrackPlayer.load(file)
  │    └─ Object URLを<audio>のsrcへ設定 ── 後で再生する経路
  │
  └─ analyzeTrack(file)
       └─ ArrayBuffer → AudioBuffer → 波形解析 ── 譜面を作る経路
```

`TrackPlayer.load()` はブラウザ内のローカルファイルURLを作り、`<audio>` の再生元として設定します。一方、解析側はファイルをPCM波形へデコードします。解析用の `AudioContext` はデコード後に閉じ、実際の再生時計には `<audio>.currentTime` を使います。この分離により、解析処理の時計ではなく、ユーザーが実際に聞いている再生・一時停止可能な時計を判定基準にできます。

### 3. 解析と譜面生成

`loadTrack()` はゲームを `analyzing` にして `analyzeTrack()` を待ちます。解析中は進捗コールバックが `analysisProgress` を更新し、p5.jsの通常の描画ループが進捗バーを描き続けます。長い波形ループも一定間隔でブラウザへ制御を返すため、別ファイルの選択と解析中止が可能です。

楽曲から `AnalysisBeat[]` を作るデータの流れは次のとおりです。各 `AnalysisBeat` は判定時刻 `time`（秒）と立ち上がりの相対的な強さ `strength` を持ちます。

```text
圧縮音声（MP3、WAVなど）
  ↓ decodeAudioData()
チャンネル別PCMサンプル
  ↓ 512サンプル区間ごとに低・中・高域と全体のRMSを計算
帯域別の音量時系列
  ↓ 対数圧縮し、直前より増えた量を帯域別に重み付け
novelty（音の立ち上がり量）の時系列
  ↓ 局所最大 + 中央値/MADによる動的閾値 + 最低音量
細かなonset候補
  ├─ 区間別BPM推定に成功
  │    ↓ BPMグリッドを骨格にし、近傍onsetへ時刻を寄せる
  │    ↓ 強い裏拍を追加し、過密・無音の点を抑える
  │    └─ tempo-grid譜面
  │
  └─ BPM推定失敗、または生成点が少なすぎる
       ↓ 0.48秒未満の近接onsetは強い方へ整理
       ↓ まだ少なければ0.82秒区間ごとの最大noveltyを採用
       └─ onset譜面
```

BPMグリッドだけをそのまま譜面にはしません。BPMは周期的な「目盛り」の間隔を安定させるために使い、最終的な判定時刻は近くで実際に音が立ち上がったonsetへ寄せます。さらに強い格子外onsetを追加するため、裏拍やシンコペーションも一定範囲で残ります。反対に、速すぎる曲ではグリッドを整数拍ごとに間引き、onsetが十分ある曲では音のないグリッド点を減らします。これは自動採譜の正確さそのものより、「聞こえる音に合い、手拍子できる密度」を優先したゲーム用の譜面生成です。各計算条件は後述の「曲のリズムポイント生成」で詳しく説明します。

解析が完了すると、`loadTrack()` は結果を `analysis` に保存し、`RhythmGame.configure(result.beats)` へ判定点列を渡します。`configure()` は各点へ `hit`、`shifted`、`resolved`、`pieceCreated` の処理状態を付け、得点と盤面をリセットしてゲームを `ready` にします。解析に失敗した場合や、途中で選び直された古い解析結果は譜面として採用されません。

### 4. ゲーム開始から終了まで

READY画面では、START操作の前にマイクを準備できます。`MicrophoneInput.start()` は権限取得後に約900 msの環境音を測り、入力閾値を決めます。Spaceなら `beginPlayback(false)` を呼び、マイクなしで直接開始できます。

`beginPlayback()` は新規プレイなら曲を先頭へ戻して `RhythmGame.startFresh()` を呼び、一時停止からなら `resume()` を呼びます。その後に `<audio>.play()` を開始します。プレイ中の各描画フレームでは、`updateGame()` が次の順に処理します。

1. マイク波形を `MicrophoneInput.update(performance.now())` で更新し、手拍子を検出した場合は `registerHit("mic")` へ渡します。Spaceとステージ/TAPの操作も `registerHit("manual")` へ集約されます。
2. `registerHit()` は `<audio>.currentTime` を曲中時刻として `RhythmGame.registerInput()` を呼びます。マイクだけは検出遅延の概算35 msを差し引きます。ゲームは許容窓内で最も近い未確定点を探し、PERFECT/OKなら得点・コンボ・画像生成予約を、対応点がなければNGを記録します。
3. 続いて `RhythmGame.advance()` が現在の曲時刻まで譜面を進めます。判定点の時刻ごとに全画像を1列左へ送り、成功済みなら新しい画像を右端へ生成します。遅判定の終了まで入力がなければMISSを確定します。一度画像を獲得した後、MISSによって全画像が画面外へ流れた時点でゲームオーバーです。
4. 更新後、`drawStage()` が同じゲーム状態から画像列、未来の判定点レール、直近判定を描きます。論理的な列移動は一瞬で確定していますが、表示では `fromColumn` と `column` の間を100 msで補間します。成功画像も落下・行き過ぎ・跳ね返りを約140 msで描くため、判定ロジックとアニメーションを混同せずに保てます。

`<audio>` の `ended` イベントでは `finishGame()` が `RhythmGame.finish()` を呼びます。描画より先に曲末イベントが届いても、未処理の判定点を最後まで進めてから、画面内に画像が1枚以上あれば `clear`、なければ `gameover` と確定します。一時停止では曲、マイク、ゲームの3つをそろえて止め、再開後も `<audio>.currentTime` を共通基準にするため判定点との対応を維持します。

## `src/audio.ts`を読むための前提知識

TypeScriptの構文、`Promise`、DOM API、TypedArrayの読み方は理解しているものとします。音楽・物理・統計については、下表の意味が分かれば読めるようにコメントしています。楽譜の読み方、音階・コード・和声、微積分、フーリエ変換は前提にしません。この実装はFFTを使わず、周波数帯を軽量なフィルターで近似しています。

| 用語 | このREADMEとコードでの意味 | ゲームで何に使うか |
| --- | --- | --- |
| 音声サンプル / `sampleRate` / チャンネル | サンプルは、ある瞬間の波形の振れを表す数値です。`sampleRate` は1秒あたりのサンプルフレーム数、チャンネルは左右など同時刻の波形の組です。 | 左右を別々に512サンプルずつ解析し、二乗したパワーをチャンネル間で平均します。44,100 Hzなら512サンプルは約11.6 msです。波形を先に平均しないため、左右が逆位相でも相殺しにくくなります。 |
| 振幅 / RMS / peak | 振幅は波形の瞬間値、RMSは `sqrt((x1² + … + xN²) / N)` で求める区間全体の大きさ、peakは区間内の絶対値の最大です。ここでの値は校正されたPaやdB SPLではなく相対値です。 | 曲では帯域ごとの立ち上がりと無音区間を探し、マイクではRMSとpeakを両方使って短く鋭い手拍子を選びます。 |
| 周波数 / Hz / ローパスフィルター | Hzは1秒あたりの振動回数です。ローパスは低い周波数を主に残しますが、境界で完全に二分するものではありません。 | 220 Hzと2,400 Hzのローパスおよびその差から低・中・高域を近似し、キックから手拍子までの立ち上がりを拾います。 |
| 拍 / BPM / onset | 拍は曲から感じる規則的な脈、BPMは1分あたりの拍数です。したがって1拍の間隔は `60 / BPM` 秒です。onsetは、低・中・高域で対数圧縮したRMSの増加を合成した「新しい音らしさ」が大きい時刻の候補で、拍そのものとは限りません。 | BPMグリッドは拍の骨格を作り、近くのonsetへ最終判定時刻を合わせます。強い格子外onsetは裏拍・シンコペーション候補にもなり、`strength` は選択とレール線幅に使います。 |
| offset / グリッドの位相 | このREADMEでの位相は音波の山・谷の角度ではなく、「等間隔の目盛りを曲の何秒目から並べるか」です。推定offsetは小節頭や音楽理論上の強拍を保証しません。 | 高BPMで何拍かおきに間引く際、近くて強いonsetが多く重なる開始位置を選びます。グリッドは拍の所属を決め、判定時刻は近傍onsetへ合わせます。 |
| 中央値 / MAD / パーセンタイル | 中央値は並べた値の中央、MADは `median(abs(x - median(x)))` で求める通常値からの散らばりです。80パーセンタイルは、小さい順に80%の位置の値です。 | 一部の大音量に引っ張られにくい動的閾値と、マイクの初期ノイズフロアを作ります。 |
| 平滑化 / ヒステリシス | `state += (input - state) × rate` は、値を新しい入力へ少しずつ近づけます。ヒステリシスは、検出する閾値と再待機する閾値を分ける考え方です。 | マイクメーターと環境音の基準を滑らかにし、1回の手拍子の山や余韻を複数入力として数えないようにします。 |

時刻の単位は2種類あります。曲の解析結果、`TrackPlayer.currentTime`、`RhythmGame` の判定点は**秒**です。一方、`MicrophoneInput.update(now)` の `now`、900 msの初期調整、170 msの再発火防止などは `performance.now()` を基準にした**ミリ秒**です。マイクが発火した後は `index.ts` が再生時刻を35 msだけ戻し、入力処理の遅れを概算補正してからゲーム判定へ渡します。

前提を補う資料は、次の順に読むと実装へ対応しやすくなります。

- [ビートとテンポ（Ableton Learning Music）](https://learningmusic.ableton.com/ja/make-beats/beat-and-tempo.html): 拍とBPMを音を鳴らしながら確認できます。
- [Web Audio APIに関わる基本概念（MDN）](https://developer.mozilla.org/ja/docs/Web/API/Web_Audio_API/Basic_concepts_behind_Web_Audio_API): サンプル、サンプルフレーム、`sampleRate`、チャンネル、`AnalyserNode` の説明です。
- [音に関する単位変換など（東京藝術大学）](https://www.geidai.ac.jp/~marui/julialang/audio/node1.html): 振幅、対数、RMSの式を確認できます。Juliaの構文を覚える必要はありません。
- [中心的な傾向を捉える（総務省統計局）](https://www.stat.go.jp/naruhodo/5_tokucho/chushin.html): 中央値と、平均値より外れ値の影響を受けにくい理由を学べます。

## 曲のリズムポイント生成

曲に既存の譜面を用意するのではなく、選択された音声からゲーム用の判定点を毎回生成します。解析結果は、判定時刻 `time` と表示用の強さ `strength` を持つ配列です。

### 1. 音の立ち上がり（onset）を抽出

1. `AudioContext.decodeAudioData()` で音声をデコードし、複数チャンネルを個別にフィルター処理します。各チャンネルを二乗してから平均するため、左右に逆向きの波形が含まれても、単純なモノラル化のように打音が相殺されません。
2. 512サンプルごとに処理し、220 Hzと2,400 Hzのone-poleローパスフィルターの差から低域・中域・高域へ分け、各帯域と全体のRMSを求めます。
3. 各帯域のRMSを対数圧縮し、直前フレームから増えた量だけを取り出します。低域を拾いやすくするため、立ち上がり量は `低域 × 1.35 + 中域 × 1.0 + 高域 × 0.82` で合成します。
4. 合成値が前後2フレームの局所最大で、かつ直前1.1秒の履歴から作る動的閾値を超えた箇所をonset候補にします。

動的閾値と候補の条件は次のとおりです。

```text
threshold = 履歴の中央値 + max(0.018, 履歴のMAD × 2.35)
候補条件  = novelty > threshold かつ 全体RMS > 0.004
```

曲頭0.38秒と曲末0.24秒は候補から除外します。BPMグリッドの位相選択には間引く前の全候補を使い、BPM推定に失敗したときのonset譜面向けには、候補が0.48秒未満の間隔で続いた場合に `strength` が大きい方だけを残します。この候補選択は、onset方式で最終的にどちらの時刻を判定点とするかにも影響します。MAD（中央値絶対偏差）を使うことで、曲中の音量変化に追従しながら急な立ち上がりを探します。

### 2. BPMグリッドへ整列

[`web-audio-beat-detector`](https://github.com/chrisguttandin/web-audio-beat-detector) で70〜190 BPMと周期グリッドの基準オフセットを推定します。16秒以上の曲は、各区間が約18秒以下になるよう曲長を均等に分けて個別にも推定し、各BPMとoffsetをその区間だけへ適用します。推定に失敗した区間だけ曲全体の推定値へ戻します。このため、ある区間のBPMを無条件に全曲へ延長せず、途中のテンポ変更へ追従できます。offsetは小節頭を保証しません。

- 間隔が0.48秒未満なら、基本間隔の整数倍にして手拍子が過密にならないよう間引きます。現在のBPM推定範囲では、125 BPMを超える曲は実質的に1拍おきになります。
- 間引きで複数の位相候補が生じた場合、各グリッドの前後 `min(100 ms, 基本間隔 × 0.24)` にあるonsetを調べます。強さだけでなくグリッドからの距離も重みにし、遠い大音量が偶然窓へ入った位相を選びにくくします。
- グリッド近傍にonsetがあれば、最終判定時刻をそのonset時刻へ合わせます。BPMは周期を安定させる骨格、onsetは実際に耳で聞こえる打点として役割を分けるため、推定offsetの誤差や演奏の前ノリ・後ノリが判定のズレになりにくくなります。
- onsetが曲長に対して十分取れている（最低2個かつ、おおむね8秒に1個以上）曲では、onsetがないグリッド点を4格子に1つの骨格だけに抑えます。検出数が少ない曲では、音が鳴っているグリッドを従来どおり残し、ごく少数の誤検出だけで譜面が疎になるのを防ぎます。活動判定の閾値は `max(0.0045, 曲全体のRMS中央値 × 0.18)` です。
- グリッドから外れたonsetのうち、曲内のonset強度の中央値以上かつ `strength >= 0.42` のものは、強い裏拍・シンコペーション候補として加えます。ただし既存点から240 ms未満なら加えず、細かすぎる連打を避けます。

この方式を解析結果では `tempo-grid` と呼びます。出力はBPMだけの完全な等間隔列ではなく、「周期の安定性」と「聞こえる発音時刻」を組み合わせた譜面です。最終判定点の `strength` はリズムレールの線の太さだけに使い、入力の判定幅や得点には影響しません。

このゲームは音高、コード、調（キー）を解析せず、判定点も音量の立ち上がりと周期だけから作ります。そのため転調前に推定したキーを後半へ誤適用することはありませんが、転調そのものを譜面へ反映する機能もありません。転調と同時にリズムやBPMが変われば、そのうちBPM変更とonsetの変化だけが反映されます。

### 3. 検出数が少ない場合のフォールバック

BPM推定が失敗した場合や、有効なグリッド点が `max(2, 曲長秒数 / 15 の切り捨て)` 個未満の場合は、隣接点が最低0.48秒空くよう整理したonset列をそのまま使います。

それでも判定点が `max(2, 曲長秒数 / 12 の切り捨て)` 個未満なら、0.82秒ごとの区間で立ち上がり量が最大の時刻を1つ選びます。この段階では動的閾値を超える必要がなく、厳密なonsetとは限りません。完全な無音でも細い判定点を作りうる、ゲームを開始不能にしないための最終フォールバックです。隣接区間内の最大位置によって判定点の間隔は変わるため、この方式では0.48秒の最小間隔も保証しません。

これらは解析結果で `onset` と表示されます。表示BPMは0.3秒より長く2.2秒未満の隣接判定点間隔について中央値を取り、2倍または半分にして70〜180 BPMの表示域へ寄せた後、整数へ丸めます。有効な間隔がなければBPMは `--` 表示になります。このBPM補正は表示だけで、すでに作った判定点時刻は動かしません。

## 手拍子の検出

マイク入力は `getUserMedia()` で取得し、`AnalyserNode` の時間波形1024サンプルから、描画フレームごとにRMSと絶対ピークを計算します。ブラウザにはモノラル、エコーキャンセル有効、自動ゲイン調整無効を希望値として渡しています。ノイズ抑制は初期状態では無効を希望し、画面の `NS OFF` / `NS ON` で切り替えられます。これはブラウザへの希望値であり、端末が実際に対応・適用する保証はありません。

### 初期調整と動的閾値

マイク開始後の約900 msは判定せず、周囲の音量を収集します。そのRMSの80パーセンタイルを初期ノイズフロアとし、プレイ中も静かな入力にゆっくり追従させます。

```text
threshold = max(0.014, noiseFloor × 3.1, slowLevel × 1.65)
```

`slowLevel` は現在の環境音へ緩やかに追従するRMSです。固定値だけでなくノイズフロアと直近の音量を使うことで、マイク感度や部屋の環境差を吸収します。

閾値バーをドラッグすると `0.006〜0.120` の相対RMS範囲で手動値に固定され、この動的閾値の代わりに検出・再待機へ使われます。左へ動かすほど小さい音を拾いやすくなりますが、環境音の誤検出も増えます。右へ動かすほど強い打音だけを拾います。手動中も環境音の測定自体は継続するため、`AUTO↺` で戻した時点から自動調整を再開できます。

### トリガー条件

次の条件をすべて満たした瞬間を、1回の手拍子として扱います。

- RMSが `直前のRMS × 1.22 + 0.0015` を超えて急上昇している。
- RMSが動的閾値を超えている。
- 絶対ピークが `max(0.1, 動的閾値 × 2.1)` を超えている。
- 前回のトリガーから170 msを超えており、検出器が再待機状態になっている。

発火後はいったん検出器を停止し、RMSが `動的閾値 × 0.58` 未満の状態で55 msを超えて続くと再待機します。これにより、持続音や1回の手拍子を複数回拾う現象を抑えます。

検出されたマイク入力は処理遅延の補正として、再生時刻から35 msを差し引いてタイミング判定へ渡します。`Space` と画面タップは補正せず、マイクと同じ判定関数へ直接渡します。

## タイミング判定とゲームルール

入力時刻と未判定のリズムポイントを比較し、許容範囲に複数の候補がある場合は時間差の絶対値が最小のものを1つだけ取得します。同じリズムポイントを2回成功させることはできません。

| 判定 | 条件 |
| --- | --- |
| `PERFECT` | リズムポイントの前後72 ms以内 |
| `OK` | 72 msより外側、かつ140 ms前〜200 ms後の範囲内 |
| `NG` | 入力に対応する未判定のリズムポイントがない |
| `MISS` | 入力がないままリズムポイントの200 ms後を過ぎた |

画面上では `PERFECT` と `OK` を成功の `OK!`、範囲外入力と `MISS` を失敗の `NG` として集計・表示します。

- 成功時の基本点は `PERFECT = 1,000`、`OK = 700` です。さらに `min(500, 現在のコンボ × 18)` が加算されます。
- 範囲外入力または `MISS` でコンボが0に戻ります。
- リズムポイントの時刻になると、成否にかかわらず既存の画像列が1段左へ移動します。早めの成功入力は予約され、判定点の時刻に画像を生成します。遅めの成功入力は、その場で画像を生成します。
- 盤面は5つの論理列を持ち、新しい画像は右端へ入ります。画面外かどうかは、レスポンシブな描画サイズと各画像の実寸を使って判定します。

## リポジトリ構成

| パス | 役割 |
| --- | --- |
| `index.html` | p5.jsのマウント先、音声ファイル入力、`audio`要素、スクリーンリーダー向け通知領域を定義するHTMLエントリ |
| `index.ts` | ファイル選択、解析・再生制御、マイク／キー／タップ入力、レスポンシブUI、画像アニメーションを統合するエントリポイント |
| `src/audio.ts` | 音声解析、BPMグリッド生成、フォールバック、音声再生、マイク入力と手拍子検出 |
| `src/game.ts` | ゲームの状態遷移、タイミング判定、得点・コンボ、画像列、クリア／ゲームオーバー判定 |
| `src/audio.test.ts` | BPMグリッド、高BPM時の間引き、無音区間除外のユニットテスト |
| `src/game.test.ts` | 判定点の取得、歯抜け列、画像循環、クリア／ゲームオーバー条件のユニットテスト |
| `src/assets.d.ts` | `.PNG` をTypeScriptからファイルとしてimportするための型宣言 |
| `public/1.PNG`〜`public/7.PNG` | 順番に表示する1920×1080の画像素材。描画時は人物部分を切り抜いて使用 |
| `Composition.json` | Cavalryから書き出した1920×1080のモーション設計参照データ |
| `Composition.mp4` | 連続成功時の演出を検討するための参照映像 |
| `package.json` | Bunのスクリプトとp5.jsなどの依存関係 |
| `bun.lock` | Bunが解決した依存バージョンのロックファイル |
| `tsconfig.json` | DOM／ESNext、strictモードなどのTypeScript設定 |
| `dist/` | `bun run build` が生成する静的配信用ファイル（Git管理対象外） |

`Composition.json` と `Composition.mp4` はモーション実装時の参照資料です。現行のランタイムからは直接読み込んでおらず、落下・バウンド・左移動は `index.ts` のp5.js描画として実装しています。画像ファイルの拡張子は大文字の `.PNG` です。

## 開発・検証

```bash
# 型チェック
bun run typecheck

# ユニットテスト
bun test

# 本番用ビルド（dist/へ出力）
bun run build
```

自動テストはBPMグリッド生成とブラウザ非依存のゲームルールを中心に検証しています。音声ファイルのデコードからonset抽出までの統合処理、マイク権限、端末ごとの入力特性、描画についてはブラウザでの確認が必要です。
