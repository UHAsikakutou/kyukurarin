# きゅうくらりんリズムゲーム

[きゅうくらりん](https://www.nicovideo.jp/watch/sm39257413)のMVを模したリズムゲームである。
課題曲(音声ファイル)をアップロードすると、リズムの解析が行われる。
再生ボタンを押すと課題曲の再生が始まる。同時にマイクによる入力を受け付ける。
ユーザは再生中、手拍子や足踏みなどによってリズムを取ることができる。
そのリズムが曲のリズムと一致すると、MVを模した画像演出が作動する。

判定はリズム1回ごとに行う(=閾値以上の音圧が瞬間的に入力されるとトリガー)。これが曲の盛り上がりポイント・リズムに一致すればOK。一定のOK範囲外ならNG。
OKであればきゅうくらりんのように画面上から画像が一枚降ってくる。
NGであれば画像は降ってこない。

画像の集団は時間経過(数秒に1度)一定距離左に移動していく。
移動はNGで画像が表示されなかった場合でも同様に左に移動する。

例えば、OK→NG→OKなら、NGの箇所だけ歯抜けになった状態で画像の集団が移動していく。
画面内に画像がなくなったらゲームオーバーである。

画像内に1枚以上画像が残っている状態で曲の再生を終えればクリアである。

画像は`./public`内の数字付き画像を用いる。1.pngから順番に登場させ、次の画像がなくなれば1に戻る。
アニメーションは`./Composition.json`を参照すること。(降ってくる→左に動く のセット。)3回OKが続いた場合の映像も`./Composition.mp4`に用意している。

UIは、p5.jsで構築する。ビルドと配信にbunを使用する。その他プログラムはtypescriptで記述する。

## クイックスタート

Bunと、Web Audio APIに対応したモダンブラウザを要する。音声のデコードと再生に利用できる形式はブラウザによって決まる。

```bash
bun install
bun run dev
```

起動後、ターミナルに表示された `localhost` のURLをブラウザで開く。マイク入力にはブラウザの許可に加え、`localhost` またはHTTPSのセキュアな環境が必要である。マイク利用時は、曲の再生音との分離にヘッドホンを利用できる。

## 操作方法

| 操作 | 動作 |
| --- | --- |
| `曲を選ぶ` / `O` / `U` | 音声ファイルを選択 |
| `MICを準備` | マイクの許可を求め、入力レベルを調整 |
| マイクの閾値バーをドラッグ | 入力閾値を手動値へ固定（左側は低い閾値、右側は高い閾値） |
| `AUTO↺` | 手動閾値を解除し、環境音に応じた自動調整へ戻す |
| `NS OFF` / `NS ON` | ブラウザへ要求するノイズ抑制を切り替える |
| `設定` → 再生音量 | 曲の再生音量を0〜100%で変更 |
| `設定` → 入力デバイス | 手拍子判定に使うマイクを選択（変更後は入力レベルを再調整） |
| `設定` → 出力デバイス | 対応ブラウザで曲を鳴らすスピーカーやヘッドホンを選択 |
| `START` / 再生ボタン | ゲーム開始または再開 |
| `Space` | READY画面では手動入力モードで開始、プレイ中は手拍子の代替入力 |
| ステージまたは `TAP` をタップ | プレイ中の手拍子の代替入力 |
| `P` / `Esc` / 再生ボタン | 一時停止・再開 |
| `R` | リザルト画面から同じ曲をリトライ |

マイクの利用が拒否された場合や未対応の場合も、`Space` と画面タップでプレイできる。タブが非表示になるとゲームは自動的に一時停止する。

## 処理の全体像

```text
音声ファイル
  ├─ analyzeTrack() ── BPM推定 + onset抽出 ── リズムポイント列
  └─ TrackPlayer ──────────────────────────── 曲の再生時刻
                                                     │
マイク ── MicrophoneInput ── 手拍子トリガー ────────┤
Space / タップ ── 手動トリガー ─────────────────────┤
                                                     ▼
                              RhythmGame.registerInput()
                                  │          │
                              タイミング判定  盤面・得点更新
                                  └──────┬───┘
                                         ▼
                                  p5.jsによる描画
```

`index.ts` がファイル選択、解析、再生、入力、ゲーム状態、p5.jsの描画をつなぐ。曲とマイクに関する処理は `src/audio.ts`、判定と盤面状態は `src/game.ts` に分割している。

## エントリポイントから見た処理の流れ

### 1. ページ読み込みと初期化

1. `index.html` がエントリポイントの `index.ts` を読み込む。`index.ts` は `#app`、非表示の `<audio>`、音声ファイル入力、スクリーンリーダー用通知領域を取得する。`requireElement()` は必須要素の取得と存在確認を担当する。
2. `<audio>` を包む `TrackPlayer`、マイクを管理する `MicrophoneInput`、判定と盤面の状態を持つ `RhythmGame` を1つずつ生成する。この時点のゲームフェーズは `idle` で、音声と譜面は未設定である。
3. `new p5(...)` が全画面キャンバスを作り、`public/1.PNG`〜`7.PNG` を並行して読み込む。画像が読めなかった場合も1×1 pxの代替画像で起動を続け、ゲーム中は番号付きの枠を描く。
4. 以後、p5.jsの `draw()` が毎フレーム実行される。ウィンドウ寸法からレイアウトを再計算し、ゲーム更新、ヘッダー、ステージ、フッターの順に描画する。したがってリサイズ時も、ゲームの論理列を変えずに画像の表示位置と画面内判定だけが新しい寸法へ追従する。

### 2. 音声ファイルの読み込み

ファイル入力の `change` イベントから `loadTrack(file)` が始まる。曲を選択するたびに、実行中の解析を `AbortController` で終了し、曲、マイク、解析結果を新しいファイル用の状態へ初期化する。

同じ `File` は、ここから目的の違う2経路へ渡される。

```text
選択された File
  ├─ TrackPlayer.load(file)
  │    └─ Object URLを<audio>のsrcへ設定 ── 後で再生する経路
  │
  └─ analyzeTrack(file)
       └─ ArrayBuffer → AudioBuffer → 波形解析 ── 譜面を作る経路
```

`TrackPlayer.load()` はブラウザ内のローカルファイルURLを作り、`<audio>` の再生元として設定する。解析側は同じファイルをPCM波形へデコードする。解析用の `AudioContext` はデコード後に閉じる。入力判定、盤面更新、リズムレールは、再生と一時停止に連動する `<audio>.currentTime` を共通の曲時刻として使う。

### 3. 解析と譜面生成

`loadTrack()` はゲームを `analyzing` にして `analyzeTrack()` を待つ。解析中は進捗コールバックが `analysisProgress` を更新し、p5.jsの通常の描画ループが進捗バーを描き続ける。長い波形ループも一定間隔でブラウザへ制御を返すため、解析中も別ファイルを選択できる。

楽曲から `AnalysisBeat[]` を作るデータの流れは次のとおりである。各 `AnalysisBeat` は判定時刻 `time`（秒）と立ち上がりの相対的な強さ `strength` を持つ。

```text
圧縮音声（MP3、WAVなど）
  ↓ decodeAudioData()
チャンネル別PCMサンプル
  ↓ 512サンプル区間ごとに低・中・高域と全体のRMSを計算
帯域別の音量時系列
  ↓ 対数圧縮し、直前より増えた量を帯域別に重み付け
novelty（音の立ち上がり量）の時系列
  ↓ 局所最大 + 中央値/MADによる動的閾値 + 最低音量
細かなonset候補
  ├─ 区間別BPM推定に成功
  │    ↓ BPMグリッドを骨格にし、近傍onsetへ時刻を寄せる
  │    ↓ 強い裏拍を追加し、過密・無音の点を抑える
  │    └─ tempo-grid譜面
  │
  └─ BPM推定失敗、または生成点が少なすぎる
       ↓ 0.48秒未満の近接onsetは強い方へ整理
       ↓ まだ少なければ0.82秒区間ごとの最大noveltyを採用
       └─ onset譜面
```

BPMグリッドは周期的な「目盛り」の間隔を構成し、近傍のonsetは実際の発音位置に合わせて判定時刻を調整する。一定以上の強さを持つ格子外onsetも判定点へ追加され、裏拍やシンコペーションを譜面へ反映する。高BPMの区間ではグリッドを整数拍単位で間引き、onsetが十分に得られた区間では発音を伴う点と一定間隔の骨格点を残す。これらの処理により、発音時刻と操作間隔を組み合わせたゲーム用譜面を生成する。各計算条件は後述の「曲のリズムポイント生成」で詳しく説明する。

解析が完了すると、`loadTrack()` は現在選択中のファイルに対応する結果を `analysis` に保存し、`RhythmGame.configure(result.beats)` へ判定点列を渡す。`configure()` は各点へ `hit`、`shifted`、`resolved`、`pieceCreated` の処理状態を付け、得点と盤面をリセットしてゲームを `ready` にする。解析エラーはゲームの `error` フェーズと画面上のメッセージへ反映される。

### 4. ゲーム開始から終了まで

READY画面では、START操作の前にマイクを準備できる。`MicrophoneInput.start()` は権限取得後に約900 msの環境音を測り、入力閾値を決める。Spaceは `beginPlayback(false)` を呼び、手動入力モードで開始する。

`beginPlayback()` は新規プレイなら曲を先頭へ戻して `RhythmGame.startFresh()` を呼び、一時停止からなら `resume()` を呼ぶ。その後に `<audio>.play()` を開始する。プレイ中の各描画フレームでは、`updateGame()` が次の順に処理する。

1. マイク波形を `MicrophoneInput.update(performance.now())` で更新し、手拍子を検出した場合は `registerHit("mic")` へ渡す。Spaceとステージ/TAPの操作も `registerHit("manual")` へ集約される。
2. `registerHit()` は `<audio>.currentTime` を曲中時刻として `RhythmGame.registerInput()` を呼ぶ。マイク入力には検出遅延の概算補正として35 msを差し引いた時刻を使い、手動入力には取得時の曲中時刻を使う。ゲームは許容窓内で最も近い未確定点を探し、PERFECT/OKなら得点・コンボ・画像生成予約を、候補数が0ならNGを記録する。
3. 続いて `RhythmGame.advance()` が現在の曲時刻まで譜面を進める。判定点の時刻ごとに全画像を1列左へ送り、成功済みなら新しい画像を右端へ生成する。遅判定の終了時刻に未入力の判定点をMISSとして確定する。一度画像を獲得した後、MISSによって全画像が画面外へ流れた時点でゲームオーバーとなる。
4. 更新後、`drawStage()` が同じゲーム状態から画像列、未来の判定点レール、直近判定を描画する。列の論理位置は判定点の処理時に更新され、表示位置は `fromColumn` と `column` の間を100 msで補間する。成功画像は落下・行き過ぎ・跳ね返りを約140 msで描画する。

判定表示の下側には、解析時に実際に計算した低域・中域・高域のRMS振幅が現在時刻に合わせて流れる。薄白の破線はBPM推定ライブラリが返したBPMとoffsetを未加工で展開した拍、その上の実線はonsetへの時刻合わせ、過密点の間引き、強い裏拍の追加、無音点の除外を経た最終リズムポイントである。各リズムポイントの`L`、`M`、`H`は、低・中・高域の立ち上がりへ解析時と同じ重みを掛けた寄与率（%）を示す。最大寄与の数値と縦棒は対応するRMSグラフの色、残りの数値とonsetに結び付かないライブラリ由来の点は薄白になる。白線は上部の譜面レールの目標線と同じX座標にある現在時刻なので、振幅の立ち上がり、推定拍、実際の入力対象がどのように重なったかをプレイ中とポーズ中に比較できる。

`<audio>` の `ended` イベントでは `finishGame()` が `RhythmGame.finish()` を呼び、未処理の判定点を曲末まで進める。最終更新後に画面内の画像数を数え、1枚以上なら `clear`、0枚なら `gameover` と確定する。一時停止では曲、マイク、ゲームの3つをそろえて止め、再開後も `<audio>.currentTime` を共通基準にして判定点との対応を維持する。

## `src/audio.ts`を読むための前提知識

コードの説明は、TypeScriptの構文、`Promise`、DOM API、TypedArrayの基礎知識を前提とする。音楽・物理・統計の式は、暗記していなくても処理の目的を追えるよう、**入力した値から曲の何を取り出し、それを譜面のどこに使うか**の順で説明する。

この解析は、音程、コード、拍子、楽器名を楽譜のように採譜するものではない。主に次の2種類の情報を取り出す。

- **音が急に立ち上がった時刻**：キック、スネア、手拍子、歌い出しなど、プレイヤーが「ここで叩けそう」と感じる瞬間の候補。これをonsetと呼ぶ。
- **繰り返しの速さと位置**：曲から感じる等間隔の脈の速さ（BPM）と、その目盛りを曲のどこから置くか（offset）。これをBPMグリッドとして使う。

onsetだけでは、細かな音を拾いすぎたり、滑らかな伴奏で点がなくなったりする。BPMグリッドだけでは、機械的な等間隔になり、実際の演奏がわずかに前後する位置や裏拍を表せない。そのため、**BPMグリッドで遊びやすい骨格を作り、近くのonsetへ判定時刻を合わせる**。解析結果は音楽理論上の完全な楽譜ではなく、手拍子で遊べる密度へ調整した近似譜面である。

| 用語 | このREADMEとコードでの意味 | ゲームで何に使うか |
| --- | --- | --- |
| 音声サンプル / `sampleRate` / チャンネル | サンプルは、ある瞬間の波形の振れを表す数値である。`sampleRate` は1秒あたりの記録回数、チャンネルは左右など同時刻に記録された波形の組である。 | 連続して聞こえる音を、時間順に計算できる数値列として扱う。左右は混ぜてからではなく別々に計算するため、左右で波形の正負が逆でも打音の大きさを失いにくい。 |
| 振幅 / RMS / peak | 振幅は波形の瞬間値である。RMSは `sqrt((x1² + … + xN²) / N)` で、正負に振れる値を二乗してから平均し、短い区間の音の大きさを1つの正の値へまとめる。peakは区間内の絶対値の最大である。 | 曲の解析では512サンプルごとの「低・中・高域がどれだけ鳴ったか」を比べる。マイクではRMSとpeakから、持続する環境音より短く鋭い手拍子を選ぶ。ここで扱う値は物理的な音圧ではなく、デコードされた波形内での相対値である。 |
| 周波数 / Hz / ローパスフィルター | Hzは1秒あたりの振動回数で、値が小さいほど低い音、大きいほど高い音に対応する。ローパスは、過去の値を残しながら波形へ追従することで、変化の遅い低周波を主に残す処理である。 | 220 Hz以下を低域、220〜2,400 Hz付近を中域、2,400 Hz以上を高域として緩やかに分ける。これにより、キックの低音だけでなく、スネアや手拍子の中高音も判定点候補にできる。FFTで個々の音程を調べる処理ではない。 |
| 拍 / BPM / onset | 拍は曲から感じる規則的な脈、BPMは1分あたりの拍数である。1拍の間隔は `60 / BPM` 秒になる。onsetは、直前より帯域別RMSが急に増えた「新しい音の始まりらしさ」が大きい時刻である。 | BPMから等間隔で押せる譜面の骨格を作り、onsetから実際に耳で聞こえる打点を得る。強い格子外onsetは裏拍やシンコペーションの候補にもする。シンコペーションとは、規則的な主拍から外れた位置にアクセントを置くリズムである。 |
| offset / グリッドの位相 | offsetは、BPMから作る等間隔の目盛りの「最初の1本をどこに置くか」を表す秒数である。同じBPMでもoffsetがずれると、すべての目盛りが拍の途中へずれる。 | 推定offsetで拍の位置を合わせる。高BPMを何拍かおきに間引く場合は、強いonsetが多く重なる開始位置を選び、表拍らしい側を残す。 |
| 中央値 / MAD / パーセンタイル | 中央値は値を並べた中央、MADは `median(abs(x - median(x)))` で求める「普段のばらつき」の大きさである。80パーセンタイルは、小さい順に80%の位置の値である。 | 平均値では一度の大音量に基準全体を持ち上げられやすいため、中央値とMADで「直前までの普通の変化」を求め、それより明確に大きい変化だけをonsetにする。マイクの環境音推定にも外れ値に強い代表値を使う。 |
| 平滑化 / ヒステリシス | `state += (input - state) × rate` は、値を新しい入力へ少しずつ近づける。ヒステリシスは、検出する閾値と再待機する閾値を分ける考え方である。 | マイクメーターと環境音の基準を滑らかにし、1回の手拍子の山や余韻を複数入力として数えないようにする。 |

時刻の単位は2種類ある。曲の解析結果、`TrackPlayer.currentTime`、`RhythmGame` の判定点には**秒**を使う。`MicrophoneInput.update(now)` の `now`、900 msの初期調整、170 msの再発火防止などには、`performance.now()` を基準にした**ミリ秒**を使う。マイクが発火した後は `index.ts` が再生時刻を35 msだけ戻し、入力処理の遅れを概算補正してからゲーム判定へ渡す。

前提を補う資料は、次の順に読むと実装へ対応しやすくなる。

- [ビートとテンポ（Ableton Learning Music）](https://learningmusic.ableton.com/ja/make-beats/beat-and-tempo.html): 拍とBPMを音を鳴らしながら確認できる。
- [Web Audio APIに関わる基本概念（MDN）](https://developer.mozilla.org/ja/docs/Web/API/Web_Audio_API/Basic_concepts_behind_Web_Audio_API): サンプル、サンプルフレーム、`sampleRate`、チャンネル、`AnalyserNode` の説明である。
- [音に関する単位変換など（東京藝術大学）](https://www.geidai.ac.jp/~marui/julialang/audio/node1.html): Juliaによる例を通して、振幅、対数、RMSの式を確認できる。
- [中心的な傾向を捉える（総務省統計局）](https://www.stat.go.jp/naruhodo/5_tokucho/chushin.html): 中央値と、平均値より外れ値の影響を受けにくい理由を学べる。

さらに背景を追う場合は、[フィルターの種類（東北学院大学）](https://www.mech.tohoku-gakuin.ac.jp/rde/contents/course/mechatronics/basicelec2_s.html)、[MADの定義（NIST、英語）](https://itl.nist.gov/div898/handbook/eda/section3/eda356.htm)、[onset検出の考え方（librosa、英語）](https://librosa.org/doc/main/auto_tutorials/01-intro/05-onsets.html)が参考になる。librosaの例ではFFTによる周波数解析を扱い、「対数で差を圧縮し、直前から増えた量をonset候補にする」という考え方を確認できる。

## 曲のリズムポイント生成

選択された音声ごとにゲーム用の判定点を生成する。処理を一言で表すと、**波形から「音が始まった瞬間」を探し、BPMから作った「拍の定規」と重ね、手拍子しやすい点だけを残す**ものである。

解析結果は、判定時刻 `time` と相対的な立ち上がりの強さ `strength` を持つ配列である。`strength` は「音量そのもの」ではなく、その時点の変化が直前の曲調に比べてどれほど目立ったかを0.08〜1程度へ収めた値である。候補の選別とリズムレールの線幅には使うが、入力の許容時間や得点は変えない。

### 1. 音の立ち上がり（onset）を抽出

#### 1-1. 波形を短い時間ごとの音量へ変換する

`AudioContext.decodeAudioData()` でMP3やWAVをPCMサンプル列へ変換し、512サンプルを1区間として調べる。44,100 Hzの音源なら1区間は約11.6 msであり、人が1回の打音として聞くものを細かな時間変化として追える長さである。

各チャンネルには、次のone-poleローパスフィルターを2種類適用する。

```text
state = state + alpha × (sample - state)
alpha = 1 - exp(-2π × 境界周波数 / sampleRate)
```

式を覚える必要はなく、`state`を現在の波形へ少しずつ近づける処理だと捉えればよい。急激な振動には追いつかないため、結果にはゆっくり振動する低い音が多く残る。220 Hz版と2,400 Hz版を組み合わせ、次の3つへ緩やかに分離する。

```text
低域 = 220 Hzローパスの出力
中域 = 2,400 Hzローパスの出力 - 低域
高域 = 元の波形 - 2,400 Hzローパスの出力
```

これは音程を特定する計算ではなく、**キックに多い低域、スネアや歌にも含まれる中域、手拍子やアタックに多い高域を別々に観察する**ための分類である。ある帯域だけを見て譜面が偏るのを防ぐ。

各帯域と全体について、区間内のRMSを求める。

```text
RMS = sqrt((x1² + x2² + … + xN²) / N)
```

波形は正負に振れるため、そのまま平均すると大きな音でも0に近づく。二乗してから平均することで、約11.6 msの区間が「どれくらい強く鳴っていたか」を正の1値へ変換できる。左右などのチャンネルは別々にフィルター処理して二乗した後に平均するため、左右の波形が逆向きでも打音のエネルギーを相殺しにくい。

#### 1-2. 音量ではなく「増え方」を取り出す

各帯域のRMSを次の関数で対数圧縮し、直前の区間から増えた量だけを残す。

```text
圧縮音量 = log(1 + RMS × 36)
帯域の立ち上がり = max(0, 今の圧縮音量 - 直前の圧縮音量)
novelty = 低域 × 1.35 + 中域 × 1.0 + 高域 × 0.82
```

対数圧縮は、大音量を相対的に縮め、小さい音の変化も比較対象へ残す。差の正の部分だけを使うのは、音が消えていく瞬間ではなく**新しく鳴り始めた瞬間**を探すためである。低域を1.35倍するのは拍の手掛かりになりやすいキックを拾いやすくし、高域を0.82倍するのは細かなノイズを少し抑えるためである。36、1.35、0.82は物理定数ではなく、ゲーム用の候補を得るための経験的な調整値である。

この合成値を`novelty`（新規性）と呼ぶ。値が大きい場所ほど、単に大きな音が続いている場所ではなく、「その瞬間に音の構成や強さが急に変わった」場所である。譜面上では、キック、スネア、手拍子、歌い出しなどの判定点候補になる。

#### 1-3. 曲調に応じた基準で目立つ山だけを選ぶ

`novelty`が前後2区間（44,100 Hzなら前後約23 ms）の局所最大になった場所だけを調べる。1つの立ち上がりの斜面を何個もの候補として数えず、山の頂点を代表時刻にするためである。

さらに、直前1.1秒の`novelty`から動的閾値を作る。

動的閾値と候補の条件は次のとおりである。

```text
threshold = 履歴の中央値 + max(0.018, 履歴のMAD × 2.35)
候補条件  = novelty > threshold かつ 全体RMS > 0.004
```

中央値は直前1.1秒の普段の変化量、MADはその普段のばらつきを表す。したがってこの式は、固定音量を超えた箇所ではなく、**その直前の曲調と比べて明確に急な変化**を選ぶ。静かなAメロと大音量のサビで同じ固定基準を使うより、両方から目立つ打点を拾いやすい。`0.018`は静かな区間の微小な数値揺れを除く下限、全体RMSの`0.004`はほぼ無音の場所を除く下限である。

候補時刻には512サンプル区間の中央を使い、区間先頭へ偏るのを避ける。曲頭0.38秒は履歴不足と開始直後の操作を避けるため、曲末0.24秒は遅判定の時間を残すため候補から除外する。

閾値をどれだけ上回ったかは`strength`へ変換する。BPMグリッドの位置選びには、近接候補をまだ削らないonset列を使う。BPM推定を使えない場合に直接譜面へ使うonset列では、0.48秒未満で候補が続くたびに強い方だけを残し、手拍子の連打が過密になるのを防ぐ。

### 2. BPMグリッドへ整列

onsetは実際の発音位置を示す一方、すべての音を候補にすると譜面の間隔が不規則になりやすい。そこで[`web-audio-beat-detector`](https://github.com/chrisguttandin/web-audio-beat-detector) で70〜190 BPMとoffsetを推定し、等間隔のBPMグリッドを譜面の骨格にする。

例えば120 BPMなら、`60 / 120 = 0.5`秒ごとに目盛りを置く。ただし、曲の0秒地点が必ず拍の先頭とは限らない。offsetは最初の目盛りを置く時刻であり、BPMが目盛りの**間隔**、offsetが目盛りの**横位置**を決める。

16秒以上の曲は、各区間が約18秒以下、かつ2区間とも8秒以上になるよう均等に分けて推定する。区間ごとのBPMとoffsetは対応する範囲だけへ適用し、推定できない区間では曲全体の値を使う。これにより、曲中でテンポが変わる場合も区間単位でグリッド間隔を変えられる。短い区間内の細かなテンポ揺れを連続的に追跡する処理ではない。

得られたグリッドは、次の順でゲーム用に調整する。

- `60 / BPM`で求めた基本間隔が0.48秒未満なら、その整数倍が0.48秒以上になるまで広げる。例えば180 BPMの1拍は約0.333秒なので、2拍ごとの約0.667秒にする。これはテンポを誤認したのではなく、曲の速さを保ったままプレイヤーが叩く拍だけを間引く処理である。現在の推定範囲では125 BPMを超える曲が実質的に1拍おきになる。
- 何拍かおきに間引くと、「1、3、5拍目を残す」「2、4、6拍目を残す」のような開始位置の候補が生じる。各グリッドの前後`min(100 ms, 基本間隔 × 0.24)`にあるonsetを探し、`onsetのstrength × 距離に応じた重み`の合計が最大になる位置を選ぶ。これにより、強い音が多く重なる表拍らしい側を譜面へ残す。
- 選んだグリッドの近くにonsetがあれば、最終判定時刻をグリッド上ではなくonset時刻へ移す。BPMは規則的な骨格、onsetは実際に聞こえる発音位置という役割分担である。これにより、offsetの小さな推定誤差や、演奏者が拍よりわずかに早く・遅く鳴らす「前ノリ・後ノリ」が、ゲーム上の判定ずれになりにくい。
- onsetが曲長に対して十分取れている（最低2個かつ、おおむね8秒に1個以上）曲では、近くにonsetがないグリッド点を4格子に1つまで減らす。機械的な全拍譜面が、解析で得た固有のリズムを覆い隠さないためである。onsetが少ない曲では、グリッド前後約90 msに音が鳴っていれば点を残す。活動判定の閾値は`max(0.0045, 曲全体のRMS中央値 × 0.18)`で、休符やほぼ無音の場所へ判定点を置きにくくする。
- グリッドから外れたonsetでも、曲内のonset強度の中央値以上かつ`strength >= 0.42`なら、目立つ裏拍・シンコペーションとして追加する。ただし既存点から240 ms以上離し、特徴的なリズムを残しながら非現実的な連打を避ける。

この方式を解析結果では `tempo-grid` と呼ぶ。出力には、BPMから得た周期とonsetから得た発音時刻の両方が反映される。最終判定点の `strength` はリズムレールの線の太さに使う。入力の判定幅と得点は、全判定点で共通の規則に従う。

譜面生成の解析対象は、帯域別音量の立ち上がりとBPMによる周期である。音程や調性は解析していないため、転調そのものは検出しない。転調と同時にリズム、打音、BPMも変わった場合に限り、その変化がonsetやグリッドを通して間接的に譜面へ現れる。

### 3. 検出数が少ない場合のフォールバック

BPMが推定できない曲でもゲームを開始できるよう、2段階の代替手段を持つ。

まず、BPM推定が失敗した場合や、有効なグリッド点が`max(2, 曲長秒数 / 15 の切り捨て)`個未満の場合は、BPMの規則性を捨て、隣接点が最低0.48秒空くよう整理したonset列をそのまま使う。テンポの骨格は弱くなるが、実際に音が立ち上がった場所を叩く譜面は維持できる。

それでも判定点が`max(2, 曲長秒数 / 12 の切り捨て)`個未満なら、曲を0.82秒ごとに区切り、各区間で`novelty`が最大の時刻を1つ選ぶ。この段階では動的閾値を超えることを要求しない。滑らかな曲や解析しにくい音源にも最低限の操作点を供給するための最終手段であり、厳密なonset検出ではない。完全な無音区間にも細い判定点が生成される場合がある。また、各区間内の最大位置を使うので、隣り合う判定点が0.48秒未満になる場合もある。

これらの代替譜面は解析結果で`onset`と表示される。信頼できるBPM推定値がないため、0.3秒より長く2.2秒未満の隣接判定点間隔について中央値を取り、`60 / 中央値`から表示用BPMを概算する。2倍または半分にして70〜180 BPMの表示域へ寄せ、整数へ丸める。有効な間隔がなければ`--`と表示する。この値はREADY画面で譜面のおおよその密度を伝えるだけで、すでに決まった判定点時刻を動かさない。

## 手拍子の検出

マイク入力は `getUserMedia()` で取得し、`AnalyserNode` の時間波形1024サンプルから、描画フレームごとにRMSと絶対ピークを計算する。ブラウザにはモノラル、エコーキャンセル有効、自動ゲイン調整無効を希望値として渡している。ノイズ抑制の希望値は画面の `NS OFF` / `NS ON` で切り替える。実際の適用状態はブラウザと端末の対応状況によって決まる。

### 初期調整と動的閾値

マイク開始後の約900 msを環境音の収集期間とする。そのRMSの80パーセンタイルを初期ノイズフロアとし、プレイ中も静かな入力にゆっくり追従させる。

```text
threshold = max(0.014, noiseFloor × 3.1, slowLevel × 1.65)
```

`slowLevel` は現在の環境音へ緩やかに追従するRMSである。固定値だけでなくノイズフロアと直近の音量を使うことで、マイク感度や部屋の環境差を吸収する。

閾値バーをドラッグすると `0.006〜0.120` の相対RMS範囲で手動値に固定され、この動的閾値の代わりに検出・再待機へ使われる。左側ほど小さい音に反応し、右側ほど大きい音に反応する。手動中も環境音の測定を継続し、`AUTO↺` の操作時に自動調整へ反映する。

### トリガー条件

次の条件をすべて満たした瞬間を、1回の手拍子として扱う。

- RMSが `直前のRMS × 1.22 + 0.0015` を超えて急上昇している。
- RMSが動的閾値を超えている。
- 絶対ピークが `max(0.1, 動的閾値 × 2.1)` を超えている。
- 前回のトリガーから170 msを超えており、検出器が再待機状態になっている。

発火後はいったん検出器を停止し、RMSが `動的閾値 × 0.58` 未満の状態で55 msを超えて続くと再待機する。このヒステリシスによって、持続音や1回の手拍子に対する重複発火を抑える。

検出されたマイク入力は、処理遅延の補正として再生時刻から35 msを差し引いてタイミング判定へ渡す。`Space` と画面タップは取得時の再生時刻を同じ判定関数へ渡す。

## タイミング判定とゲームルール

入力時刻と未判定のリズムポイントを比較し、許容範囲に複数の候補がある場合は時間差の絶対値が最小のものを取得する。各リズムポイントに対応付ける成功入力は1回である。

| 判定 | 条件 |
| --- | --- |
| `PERFECT` | リズムポイントの前後72 ms以内 |
| `OK` | 72 msより外側、かつ140 ms前〜200 ms後の範囲内 |
| `NG` | 入力に対応する未判定のリズムポイントがない |
| `MISS` | リズムポイントの200 ms後まで未入力 |

画面上では `PERFECT` と `OK` を成功の `OK!`、範囲外入力と `MISS` を失敗の `NG` として集計・表示する。

- 成功時の基本点は `PERFECT = 1,000`、`OK = 700` である。さらに `min(500, 現在のコンボ × 18)` が加算される。
- 範囲外入力または `MISS` でコンボが0に戻る。
- リズムポイントの時刻になると、成否にかかわらず既存の画像列が1段左へ移動する。早めの成功入力は予約され、判定点の時刻に画像を生成する。遅めの成功入力は、その場で画像を生成する。
- 盤面は5つの論理列を持ち、新しい画像は右端へ入る。画面外かどうかは、レスポンシブな描画サイズと各画像の実寸を使って判定する。

## 開発・検証

```bash
# 型チェック
bun run typecheck

# ユニットテスト
bun test

# 本番用ビルド（dist/へ出力）
bun run build
```

自動テストはBPMグリッド生成とブラウザ非依存のゲームルールを中心に検証している。音声ファイルのデコードからonset抽出までの統合処理、マイク権限、端末ごとの入力特性、描画についてはブラウザでの確認が必要である。
